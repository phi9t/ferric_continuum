* Purpose

This spec is the source-grounded bridge between Ferric's existing `.scratch/`
workstreams and the evidence-bound agentic-engineering model.

It does not replace source effort trackers. It records, in one place, how each
existing workstream should be represented before new implementation proceeds:

- an Engineering Task with a Task Contract;
- a completed-work closure receipt;
- a human supervision packet;
- a stale-claim recovery question;
- an archive/deletion authority decision.

The goal is to prevent old tracker state from becoming invisible context while
the repo moves to Task Contracts, Task Runs, evidence records, and explicit
human promotion gates.

* Classification rules

- Use each source file's current org metadata as the first source of truth.
- Treat ~ready-for-agent~ as executable only after blockers are resolved and a
  Task Contract can name candidate, context, outputs, and evidence.
- Treat ~ready-for-human~ and ~needs-info~ as supervision states, not hidden
  implementation permission.
- Treat ~claimed~ as active until a run journal, branch, process, or human
  decision proves it is stale.
- Preserve resolved and done efforts as receipts unless a missing acceptance
  claim requires a new task.
- Do not flatten all pending work into one branch. Every executable unit needs
  its own Task Contract or an explicit batch contract whose review boundary is
  justified.
- Do not infer authority from tracker status. Downloading large model assets,
  launching high-cost GPU/B200 jobs, publishing, deleting, pushing, merging,
  branch movement, release preparation, and destructive cleanup remain separate
  human decisions.

* Output model

Every workstream below should end in one of four artifact shapes.

** Live task contract

A live task contract is used when an agent can execute a bounded task without a
new human decision.

Required fields:

- source tracker path;
- mode: ~delivery~, ~remediation~, ~scout~, or ~experiment~;
- authoritative context files;
- allowed change surfaces;
- outputs;
- acceptance map;
- verification commands or evidence rules;
- authorization gates;
- recovery and checkpoint policy;
- prerequisite receipts or blocking tickets.

** Closure receipt

A closure receipt is used when the implementation work is complete enough that
the next useful action is evidence preservation, not new code.

Required fields:

- source tracker path;
- final candidate commit or known candidate range;
- completed claims;
- evidence records;
- evidence gaps;
- deferred claims;
- promotion status;
- next related workstream, if any.

** Supervision packet

A supervision packet is used when the next step is a human decision.

Required fields:

- decision needed;
- why the existing contract cannot decide it;
- evidence already available;
- options;
- recommendation;
- paused work;
- exact unblock effect;
- operations that remain unauthorized.

** Stale-claim recovery packet

A stale-claim recovery packet is used when a tracker says ~claimed~ but no
active run is known.

Required fields:

- claimed ticket path;
- recorded owner/run/session if present;
- filesystem and branch evidence;
- whether an active writer is still possible;
- allowed recovery action;
- next safe state.
