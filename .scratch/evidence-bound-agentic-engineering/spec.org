* Summary

Consolidate Ferric's pending local workstreams into the evidence-bound
agentic-engineering model, then implement the local tooling that makes that
model enforceable.

This effort has two layers:

- *Consolidation*: inventory existing `.scratch/` efforts, classify their
  current state, restate live work as evidence-bound Engineering Tasks, and
  preserve completed work as candidate-bound receipts or closure records.
- *Automation*: add the contract validation, run journals, task-start,
  recovery, evidence records, task-finish, command wrappers, and supervision
  packet design needed for future work to execute under the model.

The repository already defines Engineering Task, Task Contract, Task Run, and
Agent Attempt in ~docs/agents/task-runs.md~. This spec turns those documents
into the migration and implementation queue for the current Ferric estate.

The operating loop is:

#+begin_example
Frame an outcome
  -> resolve consequential uncertainty
  -> contract a bounded task
  -> execute in evidence-producing increments
  -> independently verify a fixed candidate
  -> authorize promotion
  -> improve the method from observed failures
#+end_example

This is a local, environment-first workflow. Remote execution, distributed
delegation, deployment, publication, and destructive cleanup remain explicit
human-authorized extensions.

* Migration rules

- Preserve source trackers. Do not rewrite existing effort history to make it
  look like it was born under the evidence-bound model.
- Add evidence-bound pointers beside the existing work: contract manifests,
  receipts, candidate identities, acceptance maps, and supervision packets.
- Completed efforts get closure receipts that cite the final candidate and
  verification evidence. They do not get reopened unless the receipt inventory
  finds a missing acceptance claim.
- Live implementation efforts get one Task Contract per executable ticket or
  per approved ticket batch when the batch is the true unit of review.
- Human-blocked efforts get escalation packets that ask for a decision and
  show the paused work, options, evidence, and recommendation.
- Claimed tickets are not stolen. Consolidation must inspect whether the claim
  is active, stale, or already represented by a task run before assigning a new
  writer.
- CUDA, B200, rootfs, publication, deletion, branch movement, remote effects,
  push, merge, release, and destructive cleanup remain explicit
  human-authorized gates.
- A task can be marked ready only when its authoritative context is committed
  or intentionally identified as a local tracker artifact awaiting admission.

* Work modes

Every task contract declares exactly one mode:

- ~delivery~: specified behavior, tests, reviewed candidate, operational docs
  when needed.
- ~remediation~: defect provenance, reproduction, regression evidence,
  correction, review.
- ~scout~: bounded questions, evidence anchors, uncertainties, and recommended
  follow-up tickets.
- ~experiment~: hypothesis, fixed protocol, attempt ledger, and a supported,
  rejected, or inconclusive disposition.

* Output artifacts

Consolidation produces:

- ~.scratch/evidence-bound-agentic-engineering/pending-workstreams.org~:
  current estate ledger, ownership classification, and next action per
  workstream.
- Contract manifests or contract-manifest stubs for live tasks, using the
  schema implemented by ticket 01 when available.
- Receipt files for completed efforts where the required evidence can be
  identified without rerunning expensive work.
- Supervision packets for every human-blocked decision.
- Updated org tickets under this effort that make the migration and automation
  sequence executable by agents.

* Acceptance

This setup is complete when:

- The workflow docs define the evidence-bound method without claiming
  non-existent automation exists.
- Pending Ferric workstreams are inventoried in one durable ledger with their
  status, mode, blockers, candidate/evidence state, and next action.
- Live workstreams have evidence-bound contract stubs or machine-validated
  contracts, depending on whether the validator has landed.
- Human-blocked workstreams have decision packets instead of ambiguous
  "ready" labels.
- Completed workstreams have closure receipts or an explicit gap list.
- The task-run architecture captures dirty-worktree recovery, trajectory
  binding, checkpoints, rebinding, and finish gates.
- The implementation backlog is represented as org-mode tickets under this
  effort.
- The first automation tickets preserve existing script compatibility while
  routing through one deep task-runtime module.
- Documentation checks pass for ASCII and line length.

* Non-goals

- No remote scheduler or security broker in the initial implementation.
- No automatic push, merge, deploy, publication, or destructive cleanup.
- No raw trajectory copy into Kata.
- No replacement of Kata as the durable issue system.
- No blanket requirement for large design documents on small tasks.
- No reclassification of human-owned authority decisions as agent-ready work.
