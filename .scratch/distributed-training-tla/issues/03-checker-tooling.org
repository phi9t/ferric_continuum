* Question

How should Ferric run, record, and eventually automate TLA+ model checks?

* Context

The first model needs reproducible evidence, but the first slice should not turn
into a packaging project. Ferric now has a rootfs runner that can record command,
preflight, bwrap-plan, stdout, stderr, and result artifacts. That runner can
become the evidence carrier if TLC is available in the chosen environment.

* Options to evaluate

** Option A: Manual TLC command

Document exact commands beside each model and require humans or agents to paste
the output into tracker answers.

** Option B: Thin Python checker wrapper

Add a small Ferric wrapper that invokes TLC for a model/config pair and writes a
structured summary. The wrapper can later run through ~tools/ferric_run.py~.

** Option C: Bazel test integration

Expose model checks as Bazel targets.

* Recommended direction

Use Option B for the first implementation if TLC can be discovered without a
large dependency story. Keep Bazel integration as a later hardening ticket.

* Requirements

- Discover whether ~tlc2.TLC~, ~tla2tools.jar~, Apalache, or another checker is
  already available on the host or in the rootfs.
- Decide the source layout for formal models and checker configs.
- Decide the command shape for checking one model/config pair.
- Decide the run evidence format:
  - model path
  - config path
  - checker name and version
  - command argv
  - exit code
  - safety/liveness result summary
  - counterexample path when present
- Decide whether the first checker wrapper is allowed to require Java.
- Decide whether checker commands run directly on host for v1 or through the
  Ferric rootfs runner.

* Out of scope

- Installing checker dependencies.
- Adding CI requirements.
- Supporting every TLA+ backend.
- Parsing arbitrary TLC output perfectly.

* Evidence needed

- Tool inventory command outputs.
- Proposed source and evidence layout.
- One runnable command line for checking the first model.
- Known failure modes and how they should appear in run evidence.

* Answer

Implemented the first checker tooling as Option B: a thin host-side Python
wrapper around TLC.

Entry point:

#+begin_src sh
python3 tools/tla_check.py \
  --model formal/distributed_training/MeshPlanGood.tla \
  --config formal/distributed_training/MeshPlanGood.cfg \
  --out-dir .ferric/tla/mesh-plan-good \
  --dry-run
#+end_src

Checker discovery:

- explicit ~--tla-tools-jar~
- environment variable ~TLA_TOOLS_JAR~
- executable ~tlc~ on ~PATH~
- otherwise records unavailable-tooling evidence

Evidence format:

- ~timestamp_utc~
- ~model~
- ~config~
- ~checker~
- ~checker_version~
- ~argv~
- ~executed~
- ~ok~
- ~exit_code~ for executed runs
- ~result~ for executed TLC runs, currently one of ~success~,
  ~invariant_violation~, ~temporal_violation~, or ~checker_error~
- ~stdout~ and ~stderr~ paths for executed runs
- ~counterexample~ path for non-success executed TLC results, currently the
  stdout log containing TLC's counterexample trace
- ~message~ for missing-checker or path errors

Known behavior:

- Dry-run records evidence and exits ~0~ even when no checker is installed.
- Non-dry execution without a checker exits ~2~ and records
  ~checker = "missing"~.
- Executed TLC runs use ~-metadir <out-dir>/states~ so repeated checks do not
  collide in TLC's default state directory.
- TLC output parsing is intentionally coarse; arbitrary detailed counterexample
  parsing is out of scope for this ticket.

Verification evidence from 2026-08-22:

#+begin_src sh
python3 -m py_compile tools/tla_check.py
python3 -m unittest tests.tla_check.test_tla_check
#+end_src

Result: 7 tests passed.

The same final verification command also ran both executable models through
~tools/tla_check.py~ with ~/tmp/ferric-tla2tools.jar~:

- good fixture: exit ~0~, JSON result ~success~
- bad fixture: exit ~12~, JSON result ~invariant_violation~
