#+TYPE: plan
#+STATUS: ready-for-agent

* Purpose

This plan defines the remaining work needed to complete the DTensor mesh
simulation architecture experiment before the distributed-training TLA+ track
starts implementation.

Completion means more than choosing one of the three architecture options. The
selected direction must also have a durable simulator path that can express the
forward/backward structure needed by the TLA+ effort: mesh axes, layout
movement, collective ordering, pipeline boundaries, component-level overlap,
trace records, and failure evidence.

* Route

This is a gated wayfinder-to-implementation handoff. The current checkout
already has an approved spec, common substrate, tickets 01-08, and two
implementation plans. The remaining work should run ticket-by-ticket in
isolated worktrees. Do not start the TLA+ implementation until the DTensor
handoff ticket resolves.

* Completion definition

The DTensor mesh simulation effort is complete when all of the following are
true:

- Tickets 01-03 are marked resolved with their existing evidence.
- Ticket 04 fixes dimension-aware reduce-scatter and records passing focused
  Bazel evidence.
- Tickets 05-07 each run the same dense training-step scenario through a
  different architecture option and write option-local reports.
- Ticket 08 compares those reports and recommends one durable direction.
- Ticket 09 graduates the selected direction into the canonical simulator path
  and adds a DualPipe-level schedule tracer.
- Ticket 10 writes the handoff consumed by
  ~.scratch/distributed-training-tla/issues/00-wait-for-dtensor-mesh-simulation.org~.

* Non-negotiable constraints

- Keep dense axes as ~pp x dp_replicate x dp_shard x cp x tp~.
- Preserve separate ~dp_shard~ and ~cp~ axes; derived ~fsdp~ and ~loss~ views
  may be represented as derived views, not replacement axes.
- Use CPU f32, synchronous, single-process simulation only.
- Keep MoE/EP, sparse meshes, CUDA/NCCL, asynchronous collectives, recovery,
  and uneven/ragged shards out of the completion path unless a follow-up ticket
  explicitly reopens scope.
- Reuse the common trace namespace ~tnsr.mesh_sim_trace.v0~.
- Use the pinned Bazel binary:

#+begin_src sh
bazel
#+end_src

- Preserve unrelated dirty ~tnsr~ incorporation work.
- Commit, push, branch landing, and final architecture selection require
  explicit human authorization.

** Phase 2: Run the three architecture tracer bullets

Run tickets 05, 06, and 07 after ticket 04. They may run in separate isolated
worktrees because their intended write sets are mostly disjoint, but integration
must happen through the common substrate and shared trace vocabulary.

*** Ticket 05: Wrapper DTensor

Primary evidence:

- ~ferric_continuum/tnsr/src/dtensor/wrapper.rs~
- ~.scratch/dtensor-mesh-simulation/reports/05-wrapper-dtensor.org~

The wrapper option is the low-risk control. It should prove explicit wrapping,
redistribution, reconstruction, trace emission, and structured failure reports
without changing existing local tensor behavior.

*** Ticket 06: Tensor-native layout

Primary evidence:

- ~ferric_continuum/tnsr/src/dtensor/native.rs~
- ~ferric_continuum/tnsr/src/tensor.rs~ only if metadata cannot stay adjacent
  to the core type without touching internals
- ~.scratch/dtensor-mesh-simulation/reports/06-tensor-native-layout.org~

This option is mainly a blast-radius experiment. It must prove local tensor and
autograd behavior stays unchanged when layout metadata is absent.

*** Ticket 07: Plan-first simulation

Primary evidence:

- ~ferric_continuum/tnsr/src/dtensor/plan.rs~
- ~.scratch/dtensor-mesh-simulation/reports/07-plan-first-simulation.org~

This option is the observability experiment. It must make planned collectives,
layout transitions, injections, and executed trace events directly comparable.

Exit criteria:

- All three option reports exist.
- Each option ran the same scenario and names any unsupported semantics.
- Each option includes reference-correctness evidence, trace evidence,
  failure-localization evidence, files touched, and interface-complexity notes.

** Phase 4: Graduate the selected simulator path

Files:

- ~.scratch/dtensor-mesh-simulation/issues/09-graduate-selected-simulator.org~
- Selected implementation files from ticket 08.
- ~ferric_continuum/tnsr/tests/mesh_sim_test.rs~ or a split test file if the
  current test file becomes hard to navigate.
- ~.scratch/dtensor-mesh-simulation/reports/09-graduation.org~

Required simulator behavior:

- Expose one canonical public entrypoint for the selected simulator path.
- Keep non-selected options available only as reports or test-support code
  unless ticket 08 recommends retaining them.
- Produce a deterministic run report for the dense training-step scenario.
- Export the vocabulary the TLA+ track must inherit:
  - mesh axes and rank-coordinate ordering
  - process group construction and ordered membership
  - placement names
  - layout transition names
  - collective kinds and signatures
  - trace event names and required fields
  - failure record fields

Required DualPipe-level schedule granularity:

- A forward chunk must expose these components:
  - attention
  - all-to-all dispatch
  - MLP
  - all-to-all combine
  - PP communication
- A backward chunk must expose these components:
  - attention input-gradient
  - attention weight-gradient
  - all-to-all dispatch gradient path
  - MLP input-gradient
  - MLP weight-gradient
  - all-to-all combine gradient path
  - PP communication
- The schedule representation must allow overlap between a paired forward and
  backward chunk while still making dependencies explicit.
- The simulator must reject at least one illegal overlap or ordering case with
  structured failure context.
